*2026-11-02. Maintainer register. The brief behind two asks the maintainer made on the J-F subject's page, in the Scenarios card's Arms call box, where the record's model is greyed ("the record ran no arm") and "another model" is a free-text field holding `gpt-5.5`: (1) make that field a drop-down of models and efforts from several providers, defined in a config file with API tokens "or a better, different way"; (2) a drop-down that switches the subject the page shows. Two canvases, two SWOTs, the options weighed, the backlog items proposed. Nothing is built; no task is created. Every number comes from the code at `2a258d5` or from a run in the session: `python tests/run_tests.py` 91 of 91.*

## Verdict

**Item 1, worth doing, in three sized steps, with one correction first.** The drop-down is honest only as a list of *rows the operator wrote* (provider, endpoint, model, the efforts that model accepts, the *name* of the variable holding the key, the list price), never as a provider × model × effort product and never from a file of tokens. Effort is a second control, filled from the chosen row. Fix the price table before anything else: the harness prices every model at the record model's rate, and the default "other model" costs four times that on input and three times on output (read 2026-11-02). Google through its OpenAI-compatible endpoint and any gateway (LiteLLM, OpenRouter) fit the existing loop; Anthropic through its compatibility layer does not (effort ignored, JSON mode refused, cached tokens absent), so a Claude row goes through a gateway or waits for a native adapter nobody has asked for.

**Item 2, worth doing as a story in two steps, with a zero-code route today.** The page can switch subjects per request once the page's modules take the subject as a value instead of the module global `SUBJECT`; the harness needs nothing, it runs as a subprocess with `KG_SUBJECT` in its environment. Until then, one stack per subject by compose alone, with the ports as variables, gives the maintainer two pages side by side without a line of Python. Restarting the container from a selector is rejected.

## Item 1: a drop-down of models and efforts from several providers

### What exists

- `harness/arms.py` `endpoint()` reads three settings at call time: `KG_MODEL_BASE_URL` (default `api.openai.com`), `KG_MODEL_API_KEY_VAR` (the *name* of the variable, default `OPENAI_API_KEY`), `KG_ARMS_MODEL` (default the subject's `record_model`, else `DEFAULT_MODEL = "gpt-5.5"`). `enabled()` is true only when the named variable holds a value and the subject declares an oracle (task-0005, task-0013). The page's `/api/run` takes a free-text model matched by `MODEL_RE` and passes it to the harness subprocess as `KG_ARMS_MODEL` (`server.py` `Runner.start`); `is_deviation()` compares the model name with the record's, nothing else; `views.build` marks `model_deviation` by prefix on the model the endpoint reported (`chunk.model`).
- Effort is not sent, not recorded, not compared. The pinned SDK, openai 3.41.0, accepts `reasoning_effort` on `chat.completions.create` with the literal `none, minimal, low, medium, high, xhigh, max` (checked in a venv in the session); the loop in `agent.py` `openai_responder()` and the one-reply `arms.call()` pass none of it.
- Price: one pair, `PRICE_IN, PRICE_OUT = 1.25/1e6, 10.0/1e6`, "the record model's list price read 2026-10-30", cached at a tenth; `cost()` applies it to every model. The record model is `gpt-5.1-2025-11-13`, and OpenAI's pricing page lists gpt-5.1 at 1.25 / 0.125 / 10.00 and gpt-5.5 at 5.00 / 0.50 / 30.00 per million (input / cached / output, read 2026-11-02). So an Arms run on the default other model is under-estimated by 4× on input and 3× on output, and both dollar ceilings (`CEILING_USD = 25.0`, the agent's `KG_AGENT_MAX_USD` default 5) are weaker than they say on it. The cached ratio of a tenth is OpenAI's for the GPT-5.x rows and not a constant elsewhere (Gemini a tenth; Anthropic's cache read a fortieth to a tenth by model; OpenAI's newest rows a twentieth).
- The J-F subject's `record_model` is empty: `endpoint()["deviation"]` is false whatever is called, the page's record radio is greyed and says "the record ran no arm", and the note under the field says an Arms run compares with nothing. That marking is the behaviour the drop-down must keep.

Stated plainly: Anthropic's own page says its layer is "primarily intended to test and compare model capabilities, and is not considered a long-term or production-ready solution". The loop as written works on OpenAI and on a gateway; on Google it works for the agent arm and is unverified for the one-reply arm; on Anthropic it loses effort, JSON mode and the cache accounting, and a native port of `arms.py` and `agent.py` to the Messages API is a second client, a second message shape, a second usage shape and a second streaming parser, about the size of `agent.py` itself, for one provider.

### What "effort" means, per provider

OpenAI's effort is a named level from a model-dependent set, default medium, and `none` turns reasoning off where the model allows. Google's is a thinking level (minimal to high) on Gemini 3 and later, a token budget before, and cannot be turned off on the Pro and 3 models. Anthropic's is `output_config.effort` from low to max with adaptive thinking, default high on most models. The same word, medium, is not the same amount of thinking on any two of them, and thinking tokens are billed as output tokens on all three. One drop-down of provider × model × effort would therefore be a product with holes (xhigh on Gemini, none on Claude) and would imply a comparability the levels do not have. Effort is a second control whose options come from the chosen row, and the run records the level *as the provider spells it*.

### The honest deviation marking

A run is like-for-like with the CargoQuote record only if three things match: the model (`record_model`), the effort (the record sent none, so the API's default), and the route (api.openai.com, Chat Completions). Today only the first is compared, so a run on the record's model at `xhigh` would pass as like-for-like. The drop-down keeps the marking honest by carrying the record as its first row, synthesised from the subject manifest (model, effort empty, the default endpoint), and by comparing the run's recorded `{host, model, effort}` with it; any difference is the deviation, shown in red as today. On a subject whose record ran no arm, that row is greyed with "the record ran no arm" and nothing is a deviation, as today.

### A config file with API tokens: no, and why

Keys are read from the environment only and never committed (CLAUDE.md "Boundaries"; task-0005, task-0013; `demo/docker-compose.yml` passes `OPENAI_API_KEY` and `KG_MODEL_API_KEY` from the shell). A file of tokens breaks that in every direction at once: it is committed by accident, copied into the image by `COPY . /repo`, mounted into the container, listed by the page's source card, kept in backups, and read by anyone who can read the repository. It also turns "which provider answers" from a decision the operator makes by exporting one variable into a menu where every provider is one click away, the opposite of task-0013. The better way is the one `KG_MODEL_API_KEY_VAR` already uses, per row: the file names the *variable*, the operator exports it, and a row whose variable is empty is listed greyed with "set `VAR`" and cannot be chosen. The file then holds nothing secret and can be vendored, diffed and tested.

## Item 2: a drop-down that switches the subject

### What exists

- `harness/subject.py` loads `SUBJECT = load()` at import from `KG_SUBJECT` (default `subjects/cargo_quote`). It is imported in 13 modules and read at module level into tables: 50 references across the harness (`measures.py`, `rules.py`, `load.py`, `extract.py`, `run.py`, `plant.py`, `report.py`, `arms.py`, `tasks.py`, `kitio.py`), 20 in `views.py` (`RESULTS`, `SUITE_ORDER`, `RECORD_MODEL`, `SCENARIOS`, `ORDER`, `SYSTEMIC`, `REFERENCE`, `MAPPERS`), 8 in `register_view.py` (`REQ_ANCHOR`, `REQ_ID`, `EXPORT_MANIFEST`, `REQUIREMENTS`, `has_map()`, `load_map()`, `changed_artefact()`), 6 in `server.py` (`RECORD`, `RECORD_MODEL`, `DEFAULT_OTHER_MODEL`, the store's `instance`, the page title, the saved queries).
- The harness is never imported by the page: `Runner.start` runs `run.py` as a subprocess with the server's environment. A per-run `KG_SUBJECT` is one line there. The whole cost of item 2 is on the page side.
- State that is per subject and today lives in process or on disk unlabelled: the record and its check (`RESULTS`); the register map and the footprint (`has_map()`); the runs folder (`sources_for` lists any run folder holding the scenario id; the run carries no subject id; CargoQuote's ids S1 to S7, J-F's C and D1 to D5, minimal's S0 do not collide, by luck); the store (one database, one loaded scenario, the adapter's `instance` id stamped on writes "for a shared store later", `store_status()` naming the scenario and not its subject; the register projection is shared, rightly, one register per organisation); the arms choice (`localStorage` key `kg-arms-model`, one per browser, not per subject); the page title and subtitle (`[page]`); the CI stack job asserting S1 to S7 and the register numbers on `/api/scenarios`.
- Rules that bind: task-0002, nothing in `harness/` or `demo/` names a subject (a residue test holds the names and the export date); task-0006.01, one register per organisation shared by every subject; `docker-compose.instance.yml` mounts the instance folder read-only at `/instance` with `KG_SUBJECT=/instance/subjects/<id>`.

| (c) A selector that restarts the container with another `KG_SUBJECT` | The app re-executes itself with a changed environment, or asks Docker to restart it. | Yes. | Yes. | Small in lines, large in consequence. | Rejected: a click by one viewer changes the page for every viewer and kills a run in progress; the compose file's `KG_SUBJECT` stops telling the truth; asking Docker needs its socket in the container, which the demo must never have. |

Chosen: (a) as a story in two steps, and (b) in its honest form, one stack per subject by compose alone, as the zero-code route today: a compose project name per subject and the three ports as variables, so `KG_SUBJECT=/repo/subjects/jef_data_load docker compose -p knowgov-jef up` stands beside the default stack. That needs no Python and gives the maintainer both pages this week.

### What the drop-down costs in the controlled English

"Subject" is not a glossary term, and the page uses the word in another sense ("opens its subject's own panel" under *reference*). A selector labelled *Subject* needs the glossary entry, the two senses reconciled (the selector's is task-0002's; the panel's can become "its own panel"), and its sentences within 20 words and free of the forbidden synonyms, which the test on `index.html`'s strings enforces.
