## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found 2026-11-16 while re-recording jef_data_load for task-0357 (PR #579): three Neo4j runs of the same code on the same store gave D2's rules.R-VAGUE in three different orders (JDL-071/073/074) and D4's rules.R-REQ with JDL-118 and JDL-119 swapped. The comparator reads those lists without order, so it saw nothing; the record files themselves differ run to run, so no re-record is reproducible.

Cause: Cypher in harness/store_neo4j.py without ORDER BY, so rows come back in plan order. vague_fragments (R-VAGUE) and requirements_without (R-REQ) are the two seen; structural_violations, unresolved_assertions, declared_open, silent_entities and the other list reads (stale_on_keys, assertions_on_key, declared_gaps_for_key, derived_rows, derived_outputs, artefact_assertions, attestations, lint_gaps, act_findings, supported_by, candidate_for, fragments_with_version, requirements_verified_by, assertion_rows) have none either. The rdflib adapter iterates its graph, an order no reader can name.

Coordinator, 2026-11-16: the ordering fix goes first, as its own task and PR; #579 (task-0357's re-record) waits for it.

Rule (decision-0020's for R-CONFLICT): each read is totally ordered by id, or by key then id, and the rdflib adapter gives the same order. CargoQuote's record is not re-recorded: the comparator ignores order, so it stays valid, and its committed list order becomes one sample of a now-sorted output (a known residue, cleared at the next deliberate CargoQuote re-record).
<!-- SECTION:DESCRIPTION:END -->
